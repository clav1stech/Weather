## Sortie de git : données en assets de GitHub Release, généralisée aux flux canicule — v3.1.0
Les parquets de données quittent le versionnement git au profit d'assets d'un
Release dédié (`data-store`), partitionnés par mois — git cessait d'être un
gestionnaire de sources pour devenir une base binaire qui gonflait sans borne.
Nouvelle abstraction `core/store/` (Protocol `DataStore`) à backends
interchangeables : écriture pipeline via la CLI `gh`, lecture dashboard en
HTTPS/REST sans authentification (dépôt public, pas de `gh` sur Streamlit
Cloud), backend local pour les tests ; fonctions pures de partition mensuelle
avec preuve de round-trip (`same_rows`). Le découpage se fait sur la colonne
temporelle propre à chaque flux (`run_date` pour l'ensemble, `fetched_at` /
`valid_time` pour les annexes).

La lecture du dashboard passe par le magasin derrière le flag `WEATHER_STORE`
(absent par défaut → lecture git inchangée) ; côté pipeline, une double
écriture derrière `WEATHER_STORE_WRITE` (CI uniquement) conserve git comme
source de vérité et miroite en best-effort, non bloquant, les seules partitions
mensuelles modifiées, chaque miroir vérifié par relecture. Généralisation aux
cinq flux canicule (ensemble T850, Tx/Tn HD, observations horaires,
observations 6 min, vintages Montsouris). Non-régression vérifiée : 35 sorties
de calcul et les 7 pages du dashboard strictement identiques entre lecture git
et lecture magasin.

Fusion dans `main` : magasin resynchronisé sur l'état courant de git (le
mirroring incrémental ne rattrape jamais un retard accumulé pendant qu'une
branche n'écrit pas encore en CI, `tools/seed_store.py` reste l'outil de
rattrapage). Lecture dashboard repensée en magasin PRIMAIRE avec repli
automatique sur le parquet git en BACKUP : toute erreur du magasin (réseau,
API injoignable) ou résultat vide bascule silencieusement sur git, sur le flux
principal comme sur les quatre flux annexes — jamais de page en erreur pour
une panne du magasin tant que la double écriture continue d'alimenter git.

## Invalidation des caches après la sortie de git — v3.1.11
Le bouton « Rafraîchir » des deux dashboards ne ramenait plus les données
fraîches : les fonctions cachées recevaient leur signature sous un nom préfixé
d'un underscore, que Streamlit exclut du hachage — la clé de cache ignorait
donc la signature, et la base canicule, cachée en `cache_resource`, échappait
de surcroît au `st.cache_data.clear()` du bouton. Le paramètre est renommé
`sig` dans toutes les couches données des deux apps, la base est bornée à une
entrée de cache, et le bouton vide les trois niveaux : métadonnées du magasin
externe (mémoïsées avec TTL côté processus), `cache_data` et `cache_resource`.
Tant que les données transitaient par git, chaque commit du pipeline
redéployait l'app et purgeait les caches toutes les 2 h ; la sortie de git a
supprimé ce redémarrage implicite et rendu le défaut visible.
